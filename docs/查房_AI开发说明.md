# 《查房：改写规则》(Rounds)AI 开发说明

> 把本文件完整交给开发 AI。目标是交付可在电脑浏览器运行的 3D 游戏 Demo，而不是设计稿、静态页面或只有镜头漫游的场景。开发 AI 应直接创建项目、编写代码、运行并修复报错，最后给出启动命令和操作说明。

## 1. 一句话玩法

玩家被困在主电源中断的旧医院，走廊仍由备用电源照明，值班员持续巡查。玩家通过三条“值班指令”临时改写医院规则，利用每条指令的收益和代价躲避追捕。坚持 **60 秒**后安全门通电，玩家必须亲自跑到门前才能获胜；被值班员碰到立即失败。

**路演记忆点：**玩家按下一条指令，灯光、门或广播立刻改变；值班员随之改变行动，玩家趁机逃生。

### 现场展示优先级

这个 Demo 面向短时间现场试玩与路演。让第一次看的人在 **20 秒内**理解“值班指令会改变医院，也会带来代价”。开始页、HUD 和场景变化都要服务于这一点。

- 第一幕尽快让值班员进入玩家视野，并给出一次使用指令的时机；不要让观众先看很长的空走廊或教程。
- 每条指令的场景效果必须远处也能看懂：开灯能看见整段走廊变化；封锁时防火门明显落下、值班员真的改道；广播时病房灯亮起、值班员真的走向病房。按钮闪光或文字提示不能代替真实世界变化。
- 指令造成的代价必须在同一局里可感知。比如封门后玩家自己的近路也被堵住，不能只在说明里声称有代价。
- 60 秒内至少出现一次“发现玩家 → 玩家下指令 → 环境改变 → 值班员改变行动 → 玩家脱身或失败”的完整戏剧段落。
- 支持演示者让现场一位观众口头选择 `1`、`2` 或 `3`，然后当场按键执行；无需增加联网投票系统。即使没人参与，游戏也应独立好玩。
- 路演效果必须来自真实可玩的逻辑，不做只在演示时生效的假动画或预录结果。

## 2. 交付目标与技术约束

- 做成桌面浏览器可玩的单页 3D 游戏。优先使用 **Vite + TypeScript + Three.js**。可用现成 npm 包，但不要依赖在线模型接口或必须联网才能读取的美术资源。
- 美术以写实取向为准：可使用自制或授权清楚的医院模型、PBR 材质和贴图，并随项目本地打包；缺少素材时用比例真实、材质统一的简化模型补足。不要把纯方块灰盒当成最终美术。启动后不需要登录、API Key、下载额外模型或手动配置资源路径。
- 保持流畅、可操作、可重复游玩。优先完成游戏流程，再增加装饰。若时间紧，删减非核心视觉细节，不删减胜负、AI、三条指令和重开。
- 游戏内文字和 README 使用简体中文。玩法必须无需联网即可在本机运行；打包后用 `npm run preview` 验证正式构建，不以开发服务器能启动代替打包验证。
- 项目应包含 `README.md`，写清安装、启动、构建、按键与已知限制；提供会自行结束并返回测试结果的 `npm run test`，以及 `npm run dev`、`npm run build`、`npm run preview`。
- 不要只输出代码片段。直接生成完整项目文件，并实际运行构建检查；发现错误后继续修复。

## 3. 场景与镜头

### 地图

地图是一层旧医院，规模小而清楚：**护士站、两间病房、药房、南北两条长走廊、安全门**。南北长走廊在东西两端连通，组成一条闭环。玩家能绕着中央建筑摆脱视线；不要设置玩家或 AI 会被永久困住的死胡同。

推荐用约 **30 m × 22 m** 的平面：外圈为可通行走廊，中央用不透明墙体与护士站构成视线遮挡。外圈两侧摆放推床、药柜、屏风等大型掩体，但通道始终足够玩家通过。安全门放在地图东侧，玩家出生点在西侧，值班员出生点在北侧。

#### 可直接实现的地图基准

下面的坐标是玩法基准，不限制美术细节。以地面左上为 `(x=0,z=0)`，单位为米；玩家与 AI 均在 `y=0` 地面移动。地图边界为 `0≤x≤30, 0≤z≤22`。**可通行主路**是四条相连的矩形走廊的并集，其他区域用墙或房间实体隔开：

| 区域 | 可通行范围 | 放置内容 |
|---|---|---|
| 北走廊 | `3≤x≤27, 3≤z≤6` | 护士站可见窗口；防火门 A 在 `x=15`，横跨北走廊宽度。 |
| 南走廊 | `3≤x≤27, 16≤z≤19` | 药房窗口与药柜；防火门 B 在 `x=15`，横跨南走廊宽度。 |
| 西走廊 | `3≤x≤6, 3≤z≤19` | 病房 1 的开放门口和广播标识。 |
| 东走廊 | `24≤x≤27, 3≤z≤19` | 病房 2 的开放门口和安全门。 |

四条走廊形成一个不断开的闭环；护士站与病房、药房可以向环路开出浅凹间，放置可遮挡视线的床或柜，但不得形成第二个必经瓶颈。最窄可通行宽度至少 **1.5 m**。掩体不能直接贴在防火门、出生点或安全门前。

- 玩家出生在北走廊 `(10,4.5)`，面向东；值班员出生在 `(22,4.5)`，先面向东巡逻到 `(25,4.5)`，再转身沿北走廊向西。初始相距 12 m，不立即判定被发现；玩家能在前几秒看见值班员，获得辨认道路和指令的时间。
- 巡逻路点依次为 `(25,4.5) → (25.5,17.5) → (4.5,17.5) → (4.5,4.5) → (25,4.5)`，循环行走；搜索结束后走向最近的可达路点继续巡逻，不传送。玩家碰撞半径约 0.35 m，值班员约 0.4 m；用这些半径检查转角和掩体间距。
- 安全门位于东走廊外墙靠中段 `(27,11)`，触发区半径约 1 m。解锁前经过触发区没有胜利，解锁后接触才胜利。
- 病房广播目标点分别位于西走廊 `(4.5,11)` 与东走廊 `(25.5,11)`；护士站位于北走廊内侧 `(12,7)` 附近，药房位于南走廊内侧 `(20,15)` 附近。目标点必须在导航图上可达。
- 防火门 A、B 只占据各自所在走廊的横截面。关闭其中一扇时，另一条横向走廊仍可绕行；两扇门不可同时关闭。门打开后恢复原导航边。

从这套主路与坐标生成碰撞体和导航数据。若为了美术调整墙体或道具位置，必须重新验证：四角连通、关闭 A 时仍连通、关闭 B 时仍连通、出生点到安全门可达。不要只移动可见模型而忘记同步导航与碰撞。

所有墙、柜、推床和关闭的门都必须有碰撞；玩家和 AI 都不能穿墙。地面与墙有清楚的视觉区别。安全门在 60 秒前不可通关；倒计时结束后门边绿灯亮起，并显示到门口的引导光带或箭头。

### 镜头

第三人称跟随镜头，位于玩家后上方，初始朝东看向北走廊，让玩家与值班员都能进入画面。`WASD` 始终按当前镜头的地面前/后/左/右方向移动；角色可以转向移动方向，镜头则平滑跟随，不因按 `A/D` 突然旋转。按住鼠标右键拖动可主动水平转动，游戏画布内需阻止浏览器右键菜单。**不强制鼠标锁定**，这样玩家能直接点击 HUD 指令卡。镜头与墙相交时临时拉近，不要让墙面长时间挡住整个画面。允许用简化的角色形体，但人物、值班员、掩体必须一眼可辨。

## 4. 美术与声音风格

**风格：写实取向的医院，明亮可读，气氛克制。**空间、家具、服装与人物比例接近真实医院；材质有真实的金属、玻璃、塑料和地砖质感。不要卡通、二次元、夸张大头或玩具感，也不追求昂贵的电影级照片写实。通过安静的走廊、略不合时宜的广播和值班员逐渐靠近的脚步制造一点紧张感即可。避免血迹、怪物脸、跳吓、满屏黑雾、脏污贴图和持续红光；不要为了“恐怖”把画面压暗到看不清路。

**品质目标：第一眼像经过统一美术设计的小型游戏，而不是几个现成模型拼在一起。**用一致的比例、配色、材质、导视与光照形成完整空间。视觉焦点先是玩家和前方路线，其次是值班员与可操作的防火门；装饰不能抢走这些信息。追求整洁、舒适、克制的高级感，不靠大量特效、霓虹、过曝或极暗画面掩盖粗糙模型。

| 元素 | 视觉要求 |
|---|---|
| 环境 | 浅米色、灰白与淡绿的真实医院配色；常见的地砖、门框、导视牌、护士站台面、病床、药柜。物体尺寸接近现实，材质和标识统一，路线清晰。 |
| 灯光 | 备用电源提供均匀的冷白照明，玩家随时能看清拐角和障碍。个别灯可轻微闪烁；被发现时只用短暂红色警示灯或 UI 点缀，不把全画面染红；安全门解锁时出现绿色灯与引导光。 |
| 玩家 | 正常人体比例和简洁可信的服装，颜色与环境有足够区分。手电可作为氛围元素，但不能成为看清道路的必要条件；移动反馈自然、清楚。 |
| 值班员 | 像普通医院工作人员：真实比例的制服、胸牌、明确的剪影。通过巡查节奏、短暂停顿和突然加快脚步表现威胁，不使用畸形肢体、滑稽表情或血腥造型。远处也能认出来。 |
| UI | 极简值班记录风格：窄条、编号、打字机或终端感文字。关键状态使用清楚的大字，不让风格妨碍阅读。 |

**统一视觉规则：**墙面以暖灰白为主，地面用低饱和灰绿或浅灰，金属与玻璃只作局部材质变化；红色留给危险提示，绿色留给安全门。医院导视、病房号码、门牌、床与药柜使用一致的设计语言和真实尺寸。主光源为有方向感的顶灯，辅以柔和环境补光与接触阴影；地面不要像镜子，材质不要一会儿照片写实、一会儿纯色塑料。UI 使用同一字体体系与间距，不混用游戏默认按钮样式。

使用 Web Audio API 或本地生成的短音效即可：空调与荧光灯的轻微底噪、远近变化的脚步、偶尔响起的医院广播、发现玩家时的短促警示音、追逐时加快的脉冲、封门金属声、开门成功音。安静与声音距离比惊吓音效更重要；不要突然用过大的尖叫声吓人。浏览器音频通常需用户交互后启动，因此开始按钮应同时激活音频。提供静音按钮。音效不要盖住操作反馈。

**美术生成后的自检循环：**不要只凭代码和模型清单判断画面。实际运行游戏，在至少 `1280×720` 和 `1920×1080` 两种窗口下观察并截图：开始画面、正常巡逻的北走廊、值班员追逐、一次指令生效、安全门解锁。逐张检查以下问题，发现明显问题就修改场景、镜头、材质、灯光或 UI，再截同一机位复查：

- 第一眼能否看出这是有护士站、病房、药房导视的医院？视线是否自然落在玩家、前进路线和当前危险上？
- 同一画面中的墙、地砖、门、床、药柜和人物是否属于同一种写实程度？有没有突兀的默认方块、漂浮物、穿模、比例失衡或重复得很假的贴图？
- 正常与追逐状态都能否看清墙角、门、掩体和脚下？是否有刺眼高光、过度泛光、过暗阴影、满屏雾或红光？
- 画面是否有足够但不过量的细节：统一的门牌、科室标识、床栏、护士站台面、药柜分区？不要为了“丰富”随机堆物件挡路。
- HUD 的字号、对齐、留白是否统一；在两个分辨率下是否都不挡住追逐方向、门和角色？

模型可以简化，但不能像临时彩色积木。若使用外部素材，保留来源与许可记录并把资源打包在项目内；找不到合适素材时保持统一的简单写实材质，不随机拼接风格冲突的模型。至少进行一轮“截图→指出具体视觉问题→修改→同机位复查”。若没有实际画面检查，不能报告“美术已达到高级感”。

## 5. 玩家操作与屏幕说明

进入游戏先显示一屏简短说明，点击“开始值班”才正式计时。主说明必须能在 10 秒内读完；不要把全部数值堆在开始页：

> **躲开值班员，活过 60 秒。安全门亮起后，跑到门前逃生。**
> `WASD` 移动 · `Shift` 奔跑 · `1/2/3` 改写医院。每条指令都有代价。

指令卡片只写短名称与一句代价：`1 开灯｜你也更容易暴露`、`2 封门｜你也要绕路`、`3 广播｜之后搜查更严`。详细数值放在悬停说明或次级帮助里。第一次使用后用一条短句确认实际后果，不遮住场景。让新玩家先玩，再从反馈中理解细节。

| 操作 | 按键 |
|---|---|
| 移动 | `W A S D`，相对镜头方向 |
| 转动镜头 | 按住鼠标右键拖动；不操作时自动跟随 |
| 奔跑 | 按住 `Shift` |
| 指令：全院开灯 | `1` 或点击对应卡片 |
| 指令：封锁走廊 | `2` 或点击对应卡片 |
| 指令：广播查房 | `3` 或点击对应卡片 |
| 重新开始 | 结算界面的“再来一次”按钮，或 `R` |
| 暂停 / 继续 | `Esc` 或屏幕暂停按钮；切后台自动暂停 |
| 静音 | 屏幕上的声音按钮 |

游戏 HUD 持续显示：倒计时、当前状态（安全 / 被发现 / 正在搜索）、三条指令及各自冷却、当前任务。建议倒计时放顶部中央、任务放顶部一侧、三条指令并排放底部，体力贴近玩家或放左下；在 `1280×720` 下不得遮住角色与前方走廊。指令发动后，用简短大字说明效果和代价，例如“全院开灯：出口可见，值班员视野扩大”。广播卡片应标出“先躲开视线才能引开值班员”，避免玩家在正被盯着时误以为按键失灵。失败时写明“被值班员抓住”；胜利时显示“安全门已抵达，逃离成功”。结算按钮必须能完整重置游戏。

游戏状态明确分为 `开始页 / 游玩中 / 暂停 / 胜利 / 失败`。只有“游玩中”推进倒计时、AI、体力、指令效果和冷却；`Esc` 或暂停按钮可暂停/继续，切到后台自动暂停，回到前台需点击“继续”。胜利或失败时冻结玩法与追逐音，不再发生第二种结算。若同一更新里同时满足抓到玩家与到达已解锁安全门，**先判抓到，结果为失败**。重新开始回到新的游玩局，所有状态从初始值重建；按键失焦时清空移动与奔跑输入，避免回到页面后角色自行移动。

## 6. 核心玩法数值

以下是首轮可玩参数，不必做复杂配置界面：

- 玩家步行约 **3.4 m/s**；奔跑约 **5.0 m/s**。奔跑体力最多持续 **3 秒**，仅在步行或静止时用约 **6 秒**补满；耗尽后按住 `Shift` 也只能步行。HUD 显示体力条。奔跑声能被 **7 m** 内的值班员听见；正常步行不触发远距离听觉追踪。
- 值班员巡逻约 **2.5 m/s**，追逐约 **4.2 m/s**。值班员直线追逐有压力，玩家可以靠绕路、遮挡和指令脱身。
- 值班员正面视野约 **90°、8 m**；墙体和大型掩体遮挡视线。追逐状态丢失视线后，先去最后看见玩家的位置搜索约 **4 秒**，再回到巡逻。若在这期间再次看见或听见玩家，重新追逐。
- 值班员接近玩家到约 **0.8 m**，且两者之间无遮挡时判定抓到。判定要稳定，不要隔墙抓人。
- 60 秒倒计时结束只负责**解锁安全门**，不是自动胜利。玩家抵达已解锁的门才通关。
- 三条指令各自有 **12 秒冷却**，从成功发动时开始计时；效果时间与代价见下表。一次只能有一条指令的**主要场景效果**在执行，其余卡片暂时禁用，效果结束后恢复可用状态。广播结束后的警觉搜索不占用这个锁。指令可用时卡片高亮，冷却时显示剩余秒数。无效发动不消耗冷却，也不播放成功动画。

| 指令 | 立即可见的效果 | 玩家得到的好处 | 必须付出的代价 |
|---|---|---|---|
| `1 全院开灯` | 在正常可见的基础照明上，全部顶灯明显增亮，地面出现通往安全门的引导光，并在 HUD 上短暂标出值班员所在走廊，持续 6 秒 | 更容易判断出口方向、值班员方位与绕行路线，重复使用仍有战术价值 | 值班员视野距离在效果期间由 8 m 增至约 12 m，更容易发现玩家 |
| `2 封锁走廊` | 选中的预设防火门落下，持续 5 秒，并响起金属声 | 截断值班员当前最短追逐路线，使其改道 | 玩家也不能穿过该门，必须选择另一条环路；门绝不能永久困住任一方 |
| `3 广播查房` | 距玩家更远且可达的病房广播响起，门灯闪烁，持续 6 秒 | 值班员没有直接目视玩家时，会去广播点查看 | 广播结束后进入约 6 秒的警觉搜索；若值班员正直接看见玩家，指令不能发动 |

地图中设置 **2 个固定防火门位置**，由封锁指令选取合适的一个。先计算值班员到玩家当前位置的最短导航路径；选这条路径上、距值班员更近、且门框 1 m 内没有角色的门。若两扇门都不在路径上，或有角色站在唯一候选门框中，显示“当前无法封锁通道”，不关门也不消耗冷却。关门后立刻重算值班员路线；到时开门并恢复原导航边。不要动态生成任意位置的墙，也不要把角色推入门内。

广播选择距玩家更远、值班员可达的病房目标点；广播期间值班员朝该点移动。若它重新直接看见玩家，立即取消广播诱导并改回追逐；之后广播音效结束也不得强制把追逐改成搜索。若发动时就直接看见玩家，显示“被盯着，广播无法引开”，不播放广播也不消耗冷却。若两处广播点均不可达，同样给出失败提示、不消耗冷却。仅当广播未被目视追逐打断时，结束后才在广播点附近警觉搜索 6 秒，再恢复巡逻。

## 7. 值班员 AI 实现要求

状态为 `巡逻 → 发现/追逐 → 丢失目标/搜索 → 巡逻`。状态切换必须有灯光、音效或 HUD 反馈。

- 巡逻：沿外圈多个点移动；不能原地打转或长期撞墙。
- 发现：满足无遮挡视线，或在一定距离内听见奔跑声时触发。发现瞬间给玩家明确的红光和提示音。
- 追逐：使用网格或导航图寻路，能绕开墙体、大型掩体和关闭的防火门；追逐路线需持续更新，但不要每帧全图重算。
- 搜索：移动至最后发现玩家的位置，在附近短暂巡视；没有再次发现则恢复巡逻。
- 防卡死：若一段时间没有明显位移，重新选路或回到最近可达导航点。不要直接穿墙瞬移到玩家面前。

开发 AI 可以采用简单的二维网格 A* 或走廊路点图做导航，3D 场景负责呈现。视线判断用射线与遮挡物相交测试。碰撞和导航使用同一套障碍数据，避免“看起来有墙，AI 却认为可通行”。

**状态判定顺序：**每次更新先判断无遮挡视线，再判断 7 m 内的奔跑声，再处理广播诱导，最后处理巡逻/搜索超时。直接目视玩家始终优先于广播。看见玩家时追逐其当前可见位置；只听见奔跑声时，朝最后一次听见声音的位置移动，不得持续读取隔墙后的玩家实时坐标。失去视线且不再听见奔跑后，到最后已知位置搜索 4 秒；到点且未再次发现才返回巡逻。广播结束后的 6 秒警觉搜索优先于普通 4 秒搜索，但再次目视玩家仍立即追逐。

检测与寻路不必每帧重算：例如以固定短间隔更新感知和目标路径，角色移动与镜头每帧更新。关门、开门、广播开始和广播结束时立即触发一次重算。若门导致原路径失效，AI 应沿另一半环路绕行；不得站在门前撞满 5 秒，也不得穿门。

所有时间行为使用同一个**游玩时钟**，只在“游玩中”增加：60 秒生存计时、体力恢复、指令持续与冷却、搜索计时都不能在暂停或切后台期间偷偷推进。动画帧间隔异常变大时限制单帧模拟步长，恢复页面后不得瞬间跳过几秒玩法。

**难度检查：**新玩家不应在出生后几秒内无操作就被抓。先保证至少有几秒辨认道路与指令的时间，再根据试玩调整巡逻方向、感知距离或出生点；不要通过让 AI 穿墙、忽略指令或突然传送来制造难度。玩家也不应仅靠一直按 `Shift` 沿外环跑满 60 秒；体力限制、视线遮挡与指令选择应真正影响结果。

## 8. 实现顺序

1. 建立 Vite + TypeScript + Three.js 项目，启动显示可移动的第三人称角色与灰盒环形医院。
2. 完成碰撞、60 秒倒计时、安全门解锁、触门获胜、被抓失败、完整重开。
3. 接入值班员巡逻、视线与奔跑声侦测、追逐、搜索、寻路和防卡死。
4. 接入三条指令，确保每条都在场景中发生真实变化，并同时具有收益和代价。
5. 加入写实取向的医院美术、明亮可读的灯光、克制的紧张气氛、UI 与声音。
6. 实际运行游戏并修复问题；执行 `npm run build`。至少人工验证一次胜利、一次失败、一次重开，以及三条指令各发动一次。

开发时把地图、计时、AI 状态与指令规则分成独立模块，渲染和声音从规则状态读取结果。这样同一规则可以被自动测试，也避免 UI 显示与实际碰撞/导航不一致。不要因追求架构而拖延可玩版本。

## 9. 验收标准

- 首次进入无需开发者解释，就能看懂目标和按键。
- 一局能从开始玩到失败或胜利，胜利必须在门解锁后亲自抵达门口。
- 玩家能利用遮挡与至少一条指令摆脱追逐一次；指令不是纯视觉特效。
- 值班员不会穿墙、隔墙抓人、长期卡在门框或被防火门永久关住。
- 每条指令的收益和代价在游玩中都能被观察到。
- 重开后倒计时、门状态、玩家位置、值班员状态、指令冷却和音效状态全部复位。
- 3 分钟展示内可以完成：说明玩法、演示至少两条指令、触发一次追逐、展示获胜或失败结算。
- `npm run build` 成功，README 中的操作与实际游戏一致。
- 用最新 Chrome 或 Edge 在普通笔记本分辨率（至少 1280×720）实际试玩，不出现阻断游戏的控制台错误；画面在追逐和关门时保持可操作。刷新页面后能重新开始。
- 浏览器切到后台时暂停计时、AI 和主要音效；回到页面显示“继续”按钮，不能靠切后台白等 60 秒通关。
