# 《午夜值班》开发与玩家验收

读取项目中的 `午夜值班_AI开发说明.md` 作为玩法与美术规格；若文件不在项目内，先向使用者索取规格。交付目标是能运行、能试玩、能从开始走到胜负并重开的 3D Demo。

若按三阶段提示词开发，按当前阶段验收并明确哪些后续工作尚未完成；第一阶段的灰盒不因缺少最终美术而失败，第三阶段交付前必须完成全部画面检查。

## 1. 用 TDD 守住核心规则

对每个新增或修复的**可判定玩法规则**，先写一个会因缺少该行为而失败的测试，再实现最小改动使其通过，最后运行相关测试与构建。测试应模拟玩家可观察到的结果，避免只断言内部函数名、文案或实现步骤。

优先覆盖这些高风险行为；已有可靠测试的项目只补缺口：

- 60 秒结束只解锁安全门；玩家到达已解锁门才胜利；被抓立即失败。
- 开始、暂停和结算状态不推进游玩时钟；同一更新既触发抓取又触发到门时按规格判失败，且只结算一次。
- 重开复位倒计时、门、玩家、值班员状态、指令冷却与临时效果。
- 三条指令各有实际收益、代价、持续时间和冷却；不能通过连按无限叠加。
- 无效封门或被直接目视时的广播应给出失败提示且不消耗冷却；成功关门后立刻改变 AI 路线，到时恢复导航。
- 视线被墙或大型掩体挡住时不能发现或隔墙抓人；奔跑声只在有效距离触发。
- 奔跑体力耗尽时降为步行，步行或静止时恢复；只听见声音的 AI 前往最后声源位置，不能透墙追踪玩家实时位置。
- 防火门关闭时玩家与值班员均不能穿过，地图仍有可通行环路；重新开门后导航恢复。
- 开灯效果期间能看到值班员所在走廊，且它的视野扩大；效果结束后两者都恢复。

将计时、状态转换、冷却和地图可达性尽量放入可测试的纯逻辑模块。使用假时钟或可控步进验证时间行为，避免真实等待 60 秒。对 AI 寻路至少测试静态障碍与防火门开关两种地图。测试框架沿用项目现有选择；新建 Vite 项目可选 Vitest。提供并运行会自行结束的 `npm run test`。不要为了覆盖率堆砌与实现同构的测试。

## 2. 像首次游玩的玩家一样试玩

自动测试通过后，实际启动游戏，用浏览器或可用的交互自动化从启动页开始操作。不要只检查截图或控制台。至少完成下面一轮：

1. 不看源码，只看开始页：10 秒内能否理解目标、移动、奔跑、三条指令和胜利条件？
2. 用 `W A S D`、鼠标和 `Shift` 移动：方向是否符合镜头、镜头是否遮挡道路、角色是否卡墙、奔跑反馈是否明显？
3. 主动引出一次追逐，再绕掩体断开视线：能否听见或看见“被发现”和“脱身搜索”的变化？
4. 分别用 `1`、`2`、`3` 或点击卡片发动指令：每次都应看到场景变化，并感受到对应代价；冷却反馈应可读。
5. 被抓一次，检查失败原因和重开；再完成一次存活、开门、到门口获胜。必要时用测试模式缩短倒计时，但最终确认正式配置为 60 秒。
6. 重开后再玩几秒，确认没有残留的关门、红光、广播、追逐音效或旧计时。
7. 切到其他标签页一小段时间再返回：计时与 AI 应暂停，不能靠后台挂机等门解锁。

再从旁观者角度看一次实际游戏：不听开发者补充解释，20 秒内能否看懂玩家目标、所选指令和环境变化？防火门落下后值班员是否真的改道、玩家是否真的受到同一扇门影响？如果这些只在 HUD 文字里成立，继续修改画面或玩法反馈。给项目负责人一份简短的陌生玩家试玩脚本；若获得未参与开发者的实际反馈，记录其第一次误解之处并修复。没有真人反馈时明确标记未完成，不能把开发者自己的熟悉程度当成易懂的证据，也不能假称已找人试玩。

发现影响操作或理解的问题，就修复并重玩相关段落。若环境不能进行交互试玩，明确记录未验证之处，不能把构建成功称为“玩家体验已验证”。

## 3. 检查美术风格和信息可读性

从玩家镜头观察开始、巡逻、追逐、指令生效、开门与结算画面。保持规格中的**写实取向、明亮可读、气氛克制的 3D 医院**：真实比例的建筑、家具和人物，统一的地砖、金属、玻璃与塑料材质；浅米、灰白与淡绿的医院配色，备用电源提供正常可见的冷白照明。病房、药房、护士站应靠布局和标识辨认；玩家、值班员和掩体的轮廓要分得开。避免卡通、二次元、玩具感和夸张人体比例。紧张感来自脚步距离、巡查节奏、广播和局部灯光变化，不靠血腥、跳吓、持续黑暗或怪物造型。

重点检查实际游玩中的画面，而非单独欣赏静帧：

- 第一眼能看出统一设计的医院，视觉焦点落在玩家、路线、值班员和可操作的门上；房间标识、床、柜与护士站让空间有细节但不杂乱。
- 正常状态就能看清地面、拐角、障碍和前进方向；手电和局部阴影只增加气氛，不承担基本导航。
- 红色仅短暂提示危险，绿色提示出口；颜色之外也有文字、形体或声音提示。
- HUD 在常见桌面分辨率下不挡住角色与路线；倒计时、目标、指令冷却可快速扫读。
- 灯光闪烁和音效变化服务于状态反馈；避免刺眼闪烁或突然过大的惊吓音，追逐音不掩盖广播和操作音。
- 所有模型与材质要统一真实比例、质感和色调；检查穿模、漂浮物、重复贴图、镜面般的地面、过曝和过暗阴影。不要把纯方块灰盒或风格冲突的随机模型当作最终画面。

实际运行并在 `1280×720` 与 `1920×1080` 截取开始、巡逻、追逐、指令生效和安全门解锁画面。逐张写出最明显的具体问题，优先修复影响第一眼观感与可读性的三项，然后在同机位重新截图对照。若截图工具不可用，至少现场观察这些状态并说明限制。不能只检查静态模型、构建结果或 AI 自述，就声称画面“舒服、高级、完成度高”；不要用截图像素测试代替视觉判断。

## 4. 完成时报告证据

交付时简要列出：运行方式；TDD 新增或修复的关键测试及其结果；`npm run build` 结果；实际玩家流程中完成了哪些操作、胜负与重开；美术审查发现的具体问题、修改与复查结果；仍未验证或仍存在的问题。若没有亲自跑通完整流程或没有检查实际画面，明确说出停在何处。
